## API 接入

调用API需经过以下几个流程：

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/b5693b25-a9f6-4819-aa5c-0993b9f82fbf/1752808113140/253.png)

## 1\. 准备工作

需要将工作流智能体发布为API后，才能通过API调用。具体发布流程如下：

### 1.1 工作流发布为API

工作流完成开发和调试后，点击工作流画布页面的右上角的发布按钮进行发布。

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/e9ce2005-0af9-4820-bec1-f77c51581277/1752808404893/254.PNG)

在弹出的页面中，点击"发布为API"栏右侧的"配置"按钮，即可跳转到发布为API的配置页面。

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/853c7552-06e8-4cab-ac7b-15d90bbfe02c/1752808462490/255.PNG)

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/1c3b2fa0-af7b-4f0c-846e-48c56e28e567/1752808516507/256.PNG)

### 1.2 实名认证

工作流发布为API前需要进行实名认证。如果您之前没有做过实名认证，则可以找到页面中"完成实名认证"栏中的"去认证"，点击即可跳转到用户认证中心页面，开发者可在此页面按照提示进行实名认证。如果您之前已成功实名认证，则可跳过此步骤。

### 1.3 创建应用

如果您之前没有创建过应用，或者期望把该工作流绑定到一个新的应用上，则需要通过此步骤创建一个新的应用。如果您已创建过应用且希望把该工作流绑定到已有的应用上，则可以跳过此步骤。

**步骤一** ：当您希望创建一个新应用时，找到"绑定应用"栏中"立即创建"按钮，点击后即可跳转到创建应用页面。

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/d3a04f30-642b-4895-b76e-5cb3368327d9/1752808604236/257.PNG)

**步骤二** ：在创建页面中，填写应用的相关信息，点击"提交"按钮完成创建。

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/e5b6b6e8-4acb-49f6-bfd7-82be99dc1dcf/1752808649733/258.PNG)

### 1.4 绑定应用

重新回到发布API的配置页面，找到"服务接口认证信息"选项卡，在该选项卡中完成工作流和应用的绑定。具体步骤如下：

**步骤一** ：点击"选择您的要绑定的应用"下拉框，此时会显示当前账号中所有的应用名称。从中选择您需要绑定的应用。

**注意事项** ：

- **如果在下拉框中没有找到刚刚创建的应用名称，则需要刷新一下配置页面** 。
- **应用一旦绑定后无法修改，请谨慎选择** 。

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/61515af7-f7fe-4029-b0f0-5e737373cd9c/1752808759209/259.PNG)

**步骤二** ：选择完应用后，点击"立即绑定"按钮，完成应用绑定。此时，会显示调用API所需要的接口信息，APIKey，API Secret和API Flowid。

![](https://openres.xfyun.cn/xfyundoc/2025-07-18/6c636985-da88-432e-bac4-7517b2153f87/1752808815066/260.PNG)

**注意** ： **如果您的工作流有了新的改动，在API调用前，请先点击"更新绑定"按钮重新发布为API，新的改动才会在API调用中生效** 。

### 1.5 获取大模型授权

在使用API接口调用前，需要确保绑定的APPID拥有您工作流中所使用的大模型授权。开发者可在 [星火官网-星火API栏](https://xinghuo.xfyun.cn/sparkapi) 领取一些免费的额度进行体验。

当发布完工作流以及获取到相关大模型授权后，即可进行智能体API调用。

### 2.2 发起会话请求

#### 2.2.1 请求协议示例

```php
{
    "flow_id": "7265177322515169282",
    "uid": "123",
    "parameters": {
        "AGENT_USER_INPUT": "你好"
    },
    "ext": {
        "bot_id": "workflow",
        "caller": "workflow"
    },
    "stream": true,
    "chat_id": "xxx",
    "history": [
      {
        "role": "user",
        "content_type": "text",
        "content": "你好"
      },
      {
        "role": "assistant",
        "content_type": "text",
        "content": "你好,我是你的工作助手，请问有什么可以帮您？"
      }
    ]
}
```

#### 2.2.2 请求参数

**2.2.2.1 Header**

| 参数名称 | 参数值 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| Authorization | Bearer $API\_KEY | 是 | 鉴权key 鉴权码组成：Bearer {API\_KEY}:{API\_SECRET} |

**2.2.2.2 Body**

| 参数名称 | 参数类型 | 是否必须 | 说明 |
| --- | --- | --- | --- |
| flow\_id | string | 是 | 工作流id |
| uid | string | 否 | 用户id |
| stream | bool | 是 | 是否启用流式返回 流式：true 非流式：false |
| ext | object | 否 | 用于指定一些额外字段，比如一些插件隐藏字段 暂时用不到 |
| parameters | object | 是 | 工作流开始节点的输入参数及取值，你可以在指定工作流的编排页面查看参数列表 {"input1": "xxxxx", "input2": "xxxxx"} |
| chat\_id | string | 否 | 会话id，用于区分不同的工作流会话，长度不超过32位 |
| history | array of history\_message object | 否 | 历史对话信息\[history\_message object\]集合 例如 \[{"role": "user", "content\_type": "text", "content": "你好" },{"role": "assistant", "content\_type": "text", "content": "你好,我是你的工作助手，请问有什么可以帮您？" }\] |

**2.2.2.3 history\_message Object**

| 参数名称 | 参数类型 | 是否必须 | 取值范围 | 默认值 | 说明 |
| --- | --- | --- | --- | --- | --- |
| role | string | 是 | user, assistant |  | 发送这条消息的实体 user: 代表该消息是用户发送的。 assistant: 代表该消息是工作流回复的。 |
| content\_type | string | 否 | text, image | text | 消息内容的类型，当前只支持两种类型。若不填写，则默认类型为text text：表示普通文本。 image：表示图片类型。 |
| content | string | 是 |  |  | 消息内容，如果是image类型这里需要填写图片url |

在处理 history\_message object 时，首个元素的 role 必须为 user。交互历史应按照 user -> assistant -> user -> assistant 的顺序进行拼接，默认情况下，user 与 assistant 之间的一对交互视为一轮对话。按对话时间从先到后依次填充。如\[{第一次},{第二次}...\]

```php
[
  // 拼接对话历史信息:
  {"role": "user", "content_type" : "text", "content": "湖南有哪些美食"},              // 用户第一个问题   role是user,表示是用户的提问
  {"role": "assistant", "content_type" : "text", "content": "湖南有xxxxxx"},        // AI的第一个回复  role是assistant，表示是AI的回复
]
```

### 2.4 恢复运行工作流

当您的工作流执行到问答节点时，工作流会被暂时中断，并返回相应的事件ID和工作流中设定的问题。此时开发者应调用此接口把用户的答复以及事件ID等信息进行上传，重新恢复工作流的运行。

**history\_message Object**

| 参数名称 | 参数类型 | 是否必须 | 取值范围 | 默认值 | 说明 |
| --- | --- | --- | --- | --- | --- |
| role | string | 是 | user, assistant |  | 发送这条消息的实体 user: 代表该消息是用户发送的。 assistant: 代表该消息是工作流回复的。 |

| content | string | 是 |  |  | 消息内容，如果是image类型这里需要填写图片url |

在处理 history\_message object 时，首个元素的 role 必须为 user。交互历史应按照 user -> assistant -> user -> assistant 的顺序进行拼接，默认情况下，user 与 assistant 之间的一对交互视为一轮对话。按对话时间从先到后依次填充。如\[{第一次},{第二次}...\]

```php
[
  // 拼接对话历史信息:
  {"role": "user", "content_type" : "text", "content": "湖南有哪些美食"},              // 用户第一个问题   role是user,表示是用户的提问
  {"role": "assistant", "content_type" : "text", "content": "湖南有xxxxxx"},        // AI的第一个回复  role是assistant，表示是AI的回复
]
```
